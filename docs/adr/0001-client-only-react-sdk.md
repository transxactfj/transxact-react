# Client-only, hand-written React SDK over the hosted Checkout Session

The platform's ADR-0010 lists the SDKs as TypeScript then PHP, all generated by Fern, and names no React SDK. This package (`@transxact/react`) departs from that on purpose. It deliberately does less than an SDK normally would. Platform ADR-0011 keeps `sk_` keys server-to-server with no CORS on `/v1`, and there is no publishable key or client token. So the browser can never talk to Transxact directly. The SDK only covers the two browser legs of the hosted checkout (platform ADR-0003):

1. Asking the Merchant backend to create a Checkout Session, then sending the Customer to its `hostedUrl`.
2. On the Return page, asking the Merchant backend what the Checkout Session's status is.

Every call goes through a function or URL the Merchant supplies, so the SDK never holds a key and never talks to Transxact.

The SDK never accepts an amount: a price set in the browser can be edited by the Customer, so the Merchant backend alone decides it. It does generate the `Idempotency-Key` (platform ADR-0009), one per Checkout attempt, and passes it through for the Merchant backend to forward. A retried request after a lost response then replays the same Checkout Session instead of creating a second one.

It is hand-written, not Fern-generated. There is nothing in the OpenAPI spec for Fern to generate hooks from: the browser surface is the Merchant's own endpoints, not Transxact's. It has zero runtime dependencies and defines its own minimal Checkout Session types. Those types are structurally compatible with `@transxact/node` rather than imported from it, so a frontend never has to install a server SDK.

The SDK never infers an outcome from the Return page URL. Both the success and cancel URLs get `session_id`, and the hosted page follows the cancel URL for failed and expired sessions too. It always confirms through the Merchant backend, polling while the Checkout Session is still `pending`.

## Considered Options

- **Server helpers** (e.g. Next.js route handlers wrapping `@transxact/node`): framework-coupled code with real maintenance cost, for what is a few lines of Merchant code.
- **An embedded or modal checkout**: needs framing/CSP rules and a postMessage protocol on the hosted page, and conflicts with the M-PAiSA iframe and its frame-breaking.
- **A headless wallet UI**: needs the raw, Merchant-built-UI API that platform ADR-0003 deferred, plus a new client-safe key type contradicting platform ADR-0011.
- **React Native**: platform ADR-0010's "no native SDK" stance and its mobile guide already cover that. This package targets React DOM only.

Any of these can arrive later as an addition without breaking this package.
